This page is the authoritative description of the raw-HID channel between the Vandal agent and the HID-Shell payload, derived from `src/protocol.nim` and `src/transport_hid.nim`.

> **Note on the repository's `docs/PROTOCOL.md`.** The file in the repository states that payload length lives in a fixed 60-byte payload and that `flags` bits 1–7 are "reserved, must be 0." That is **out of date**. The current source encodes the payload length in the high bits of the `flags` byte (`FlagLenShift = 2`, `FlagLenMask = 0x3F`) so a receiver recovers the exact number of significant bytes without scanning for NULs. The description below reflects the code.

## Transport

- USB composite device: Keyboard (IF0) + MSC (IF1) + **Vendor HID (IF2)**.
- Vendor HID descriptor: `TUD_HID_REPORT_DESC_GENERIC_INOUT(64)`, usage page `0xFF00`, usage `0x01`. **No report ID.**
- Every report — both IN (agent → host) and OUT (host → agent) — is exactly **64 bytes**. Padding bytes are zero.
- Because the descriptor has no report ID, hidapi requires a leading `0x00` byte to be prepended on write and stripped (if present) on read. HID-Shell always allocates `FrameSize + 1` and handles both the 64- and 65-byte read shapes so all three platforms share one code path.

## Frame format

```text
offset 0   : type   u8      0x10 = CMD   (agent → host)
                              0x11 = OUT   (host → agent)
                              0x12 = CTRL  (bidirectional)
offset 1   : flags  u8      bit0   = FIN (last fragment of a logical message)
                              bit1   = reserved (must be 0)
                              bit2..7 = payload length (0..60), via FlagLenShift / FlagLenMask
offset 2-3 : seq    u16 LE  per-sender, wraps; debug / dedupe only
offset 4-63: 60 bytes of payload (the significant count is given by the length field)
```

Constants from `src/protocol.nim`:

| Constant            | Value  | Meaning                                          |
| ------------------- | ------ | ------------------------------------------------ |
| `FrameSize`         | `64`   | Total bytes per wire frame.                      |
| `FrameHeaderSize`   | `4`    | `type` + `flags` + `seq`.                        |
| `FramePayloadSize`  | `60`   | Maximum significant payload bytes per frame.     |
| `TypeCmd`           | `0x10` | agent → host command bytes.                      |
| `TypeOut`           | `0x11` | host → agent shell output bytes.                 |
| `TypeCtrl`          | `0x12` | bidirectional control message.                   |
| `FlagFin`           | `0x01` | FIN — last fragment of a logical message.        |
| `FlagLenShift`      | `2`    | Left shift of the length field inside `flags`.   |
| `FlagLenMask`       | `0x3F` | 6-bit length field (0..60).                      |

`CMD` and `OUT` payloads are raw bytes (typically UTF-8). A logical message may span several frames; only the frame with `FIN = 1` ends it.

### Encoding and decoding

- `encodeFrame(f)` writes `typ` to byte 0, packs `flags & 0x03` (FIN) together with `(len & 0x3F) << 2` into byte 1, writes the little-endian `seq` to bytes 2–3, then copies `min(payloadLen, 60)` payload bytes. The result is zero-padded to 64 bytes.
- `decodeFrame(buf)` recovers `typ`, strips the low control bits into `flags`, reads the little-endian `seq`, and computes the significant length from the high bits of `flags` (capped at the available buffer).

## CTRL subtypes

`CTRL` frames always carry `FIN = 1`. The first payload byte is the subtype; the rest is subtype-specific.

| Constant       | Value  | Direction       | Payload after subtype byte                                   |
| -------------- | ------ | --------------- | ------------------------------------------------------------ |
| `CtrlHello`    | `0x01` | host → agent    | `u16 LE proto_version`, `u8 os_id`, optional zero-padded version string |
| `CtrlHelloAck` | `0x02` | agent → host    | `u16 LE agent_proto_version`                                 |
| `CtrlPing`     | `0x03` | either          | empty                                                        |
| `CtrlPong`     | `0x04` | either          | empty                                                        |
| `CtrlCmdId`    | `0x05` | agent → host    | null-terminated UTF-8 (≤ 58 B) — tags subsequent OUT chunks  |
| `CtrlBye`      | `0x06` | either          | empty                                                        |
| `CtrlError`    | `0x07` | host → agent    | `u8 code`, UTF-8 message                                     |

The HELLO probe HID-Shell sends (`sendProbeHello`) fills the payload with `[CtrlHello, proto_version_lo, proto_version_hi, os_id]` — four significant bytes.

## OS identifiers

The `os_id` byte in a HELLO:

| Constant    | Value  | OS          |
| ----------- | ------ | ----------- |
| `OsWindows` | `0x01` | Windows     |
| `OsLinux`   | `0x02` | Linux       |
| `OsMacOS`   | `0x03` | macOS       |

Other values are reserved.

## Versioning

`ProtoVersion = 0x0001` (v1). The agent rejects a HELLO whose **high byte** (major) differs from its own, replying with an `ERROR` and publishing an MQTT shell error event.

## Lifecycle

```text
host: open vendor HID interface
host -> agent: CTRL HELLO
agent -> host: CTRL HELLO_ACK
agent: publishes {topic:"shell", type:"connected"} on MQTT

# operator types a command in the web UI
agent -> host: CTRL CMD_ID   ("c-42")
agent -> host: CMD frames    ("uname -a\n", FIN on last)
host: writes the bytes to the child shell stdin

host -> agent: OUT frames    ("Linux …\n", FIN when flushed)
agent: publishes {topic:"shell", type:"output", cmd_id:"c-42", chunk, final}

agent -> host: CTRL BYE     (operator clicked Stop)
host: closes child shell, exits
```

## Flow control

- The host honours HID polling intervals — it cannot send faster than the endpoint allows. The agent calls `tud_hid_n_ready(1)` before every TX and waits up to 1 s.
- The agent's RX is a 4 KB `StreamBuffer`. If full, OUT frames are dropped and a warning logged. The host should therefore flush on newlines or 60-byte boundaries and should not spam empty output.

## Sequence numbers

Both sides maintain an independent `u16` counter, incremented per frame and wrapping at `0xFFFF`. The receiver uses it only for diagnostic logging; out-of-order frames are not expected on a USB endpoint and are not handled.
