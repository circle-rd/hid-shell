---
title: The pump
description: The single-threaded event loop that shovels bytes between the HID link and the child shell.
---

`src/pump.nim` is the heart of the payload: a single-threaded event loop that alternates short reads from the HID link and the child shell, framing and unframing on the fly. It never blocks indefinitely — every read has a bounded wait, and the loop re-checks both sides each iteration.

## The loop

`runPump(link, child, debug)` runs while `child.isAlive()`. Each iteration does three things in order:

1. **Drain inbound HID frames** (agent → host) with a short read — `link.readFrame(IdlePollMs)` where `IdlePollMs = 5`.
2. **Drain child shell output** (host → agent) — `child.tryReadBytes(...)` of up to `ChildReadChunk = 60` bytes (one HID frame payload).
3. **Periodic liveness ping** — send a `PING` if `PingIntervalMs = 5000` ms have elapsed since the last one.

## Inbound: CMD reassembly

A logical command from the agent can span several `CMD` frames. The pump accumulates the payload bytes into `cmdAcc` and only writes them to the shell's stdin when it sees a frame with `FIN` set:

```nim
of TypeCmd:
  if f.payloadLen > 0:
    # append payload bytes to cmdAcc
  if f.isFin:
    child.writeBytes(cmdAcc)
    # … and (Windows only) echo the input back, CR → CRLF
    cmdAcc.setLen(0)
```

### Windows input echo

On Windows, `cmd.exe` driven through a pipe has no line-discipline echo (a real POSIX TTY would echo via `onlcr`/`echo`). Without server-side echo the operator types into a silent web shell. The pump therefore mirrors the input back as `OUT` bytes, converting bare `CR` to `CRLF` so xterm.js advances the cursor to the next line the way it would on a TTY.

## Inbound: CTRL handling

| Received subtype | Pump reaction |
| ---------------- | ------------- |
| `PING` (`0x03`)   | Reply with `PONG` (`0x04`). |
| `PONG` (`0x04`)   | Discard. |
| `CMD_ID` (`0x05`) | Forwarded for UI tagging; logged in debug mode. The agent ignores echoes. |
| `BYE` (`0x06`)    | Return — this ends the session. |

## Outbound: OUT framing

`sendOut()` fragments a byte buffer into `OUT` frames of at most `FramePayloadSize` (60) bytes each; the **last** fragment carries `FIN`. If any `sendFrame` fails, the pump logs and exits.

## No HELLO in the pump

Note there is **no HELLO handshake inside `runPump`**. `findVandalShell` already probed the link with a HELLO/HELLO_ACK exchange to disambiguate the agent from the other vendor-page HID devices on the host. By the time the pump runs, the agent has received exactly one HELLO and replied — re-sending it would only trigger a second `payload connected` notification in the web UI for no benefit.

## Sequence numbers

Each sender maintains an independent `u16` sequence counter (`txSeq`), incremented per frame and wrapping at `0xFFFF` via `nextSeq()`. The receiver uses it only for diagnostic logging — out-of-order frames are not expected on a USB endpoint and are not handled.

## Statistics

`PumpStats` tracks `txSeq`, `rxSeq`, `bytesIn`, and `bytesOut` for the session.
