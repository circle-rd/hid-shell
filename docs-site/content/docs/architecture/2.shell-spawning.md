---
title: Shell spawning
description: How HID-Shell launches a persistent OS shell on Windows and POSIX, and why the implementations differ.
---

`src/shell_child.nim` produces a `ShellChild` — a persistent OS shell whose stdin/stdout are byte streams the [pump](/hid-shell/docs/architecture/3.pump) marshals into HID frames. The two platforms are implemented very differently, and the reasons are load-bearing.

## POSIX (Linux / macOS) — a pseudo-terminal

On POSIX the shell is spawned on a **pseudo-terminal** rather than a plain pipe. Without a PTY:

- `bash`/`zsh` treat stdout as a non-TTY and **block-buffer** output in 4–8 KiB chunks, so the operator only sees results once enough bytes have accumulated (or on `SIGINT`).
- Colours, readline editing, and full-screen tools (`less`, `vi`, `top`) all stop working.

The spawn sequence (`spawnShellPosix()`):

1. `posix_openpt(O_RDWR or O_NOCTTY)` to get the master fd, then `grantpt` / `unlockpt`.
2. `fork()`. In the child: `setsid()`, open the slave, `ioctl(slave, TIOCSCTTY, 0)` to make it the controlling terminal, and `dup2` it onto fds 0/1/2.
3. Set `TERM=xterm-256color` and override `PS1` to `\u@vandal:\w\$ ` so the prompt is short, deterministic, and does not leak the host's custom bashrc decorations (starship, conda prefixes, multi-line prompts) that fight with xterm.js cursor tracking.
4. Exec `$SHELL` (default `/bin/bash`) with `--norc -i`, falling back to `/bin/sh -i` if `execv` returns.
5. In the parent, set the master fd non-blocking and record the child pid.

## Windows — direct Win32, no console window

On Windows HID-Shell **bypasses `std/osproc` entirely** and drives `CreateProcessW` directly, for two reasons:

1. `startProcess` does not pass `CREATE_NO_WINDOW` to `CreateProcessW`. Since the payload (`sw.exe`) is built `--app:gui` and has no console, Windows would allocate a brand-new **visible** console for the child `cmd.exe` — leaking a stray prompt-less terminal window on the victim's screen.
2. Nim's pipe-backed `Stream.readData` on Windows is **blocking**, which would deadlock the single-threaded pump the moment `cmd.exe` has nothing more to say.

The implementation (`spawnShellWindows()`):

- Creates inheritable anonymous pipes for the child's stdin and merged stdout/stderr, then clears the parent's child-side handles so EOF detection still works.
- Calls `CreateProcessW` with `CREATE_NO_WINDOW or CREATE_UNICODE_ENVIRONMENT`, a hidden `STARTUPINFO` (`SW_HIDE`), and the command line `cmd.exe /Q /K` (`/Q` silences echo, `/K` keeps the shell alive for subsequent commands).
- Reads use `PeekNamedPipe` to learn how many bytes are buffered **before** `ReadFile`, making every read strictly non-blocking.

A future revision may swap the `cmd.exe` + pipe pair for ConPTY to gain colour/readline parity with POSIX.

## Byte-stream API

Regardless of platform, the pump talks to the shell through the same five procedures:

| Procedure | Behaviour |
| --------- | --------- |
| `spawnShell()` | Returns a `ShellChild` for the current OS. |
| `writeBytes(c, data)` | Writes command bytes to the shell stdin. On Windows, lone `CR` is translated to `CRLF` in-flight (see below). |
| `tryReadBytes(c, buf, maxBytes)` | **Non-blocking** read of shell output. Returns `0` if no data is currently available. |
| `isAlive(c)` | `true` while the shell process is still running. |
| `terminate(c)` | Closes the shell — `SIGTERM` then `SIGKILL` on POSIX, graceful close then `TerminateProcess` on Windows. |

### Why lone-CR → CRLF on Windows

xterm.js (and most web terminal emulators) send a lone `CR` (`0x0D`) when the operator presses Enter — exactly what a POSIX TTY expects. But `cmd.exe` driven through a pipe has no line-discipline echo and only commits a line on `\r\n` or `\n`; a bare `CR` is buffered indefinitely and the command never runs. HID-Shell therefore translates every lone `CR` into `CRLF` in `writeBytes`, passing existing `CRLF` through untouched.
